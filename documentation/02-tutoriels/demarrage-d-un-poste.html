Démarrer un poste neuf

De la machine vide au poste qui affiche des données, en sept étapes. C'est aussi la recette de l'installateur sur site : chaque ligne dit qui l'exécute.

Durée : 10 min, base déjà créée par l'assistant Prérequis : PostgreSQL 14+ joignable, .NET 8 Desktop Runtime Renvois : T0 et T1 du plan de qualification
Accueil › 02 · Tutoriels › Démarrer un poste neuf

Étapes

1
Exploitant Récupérer l'exécutable (dossier build ou installeur Velopack) et le poser sur le poste. Aucun fichier settings.json ne se copie : il contient host, base et utilisateur, et appartient au poste.
Contrôle Le premier lancement ne doit pas afficher de message d'erreur : sans réglages, le poste ouvre l'assistant.
2
Poste L'assistant réseau s'ouvre tout seul (ConnectionConfigWindow) : hôte, port, base, utilisateur, mot de passe, SSL éventuel.
3
Exploitant Bouton Tester la connexion. Le diagnostic est rédigé en français et cite la cause (SQLSTATE traduit), jamais une trame Npgsql.
À savoir Tester ne crée rien et n'enregistre rien : il Valide uniquement le trajet poste → serveur → base.
4
Exploitant Bouton Enregistrer et fermer. Le poste reteste, et si la base est absente il la crée (« La base a été créée sur le serveur. ») — le nom de base est validé par whitelist avant tout appel, et un compte sans droit de création rend la main avec une phrase explicite. Les réglages partent ensuite dans %LocalAppData%\{NomApplication}\settings.json et le resolver de connexion se reactualise à chaud : pas besoin de redémarrer le poste.
5
Exploitant Dans un terminal, à la racine du dépôt du produit : 
dotnet tool install --global dotnet-ef --version 9.0.10   # une seule fois
dotnet ef migrations list --project Framework.Data      # contrôle de lecture
dotnet ef database update --project Framework.Data      # applique Initial + trigger
Toujours passer --project Framework.Data. Sans lui l'outil instancie le contexte hors DI et essaie de monter l'hôte de App.xaml.cs, qui plante sur la ResourceDictionary WPF.
6
Outil psql — vous vérifiez que la synchro est bien vivante : 
SELECT tgname FROM pg_trigger WHERE tgname LIKE 'TX_sync%';
-- attendu : TX_sync_Comptes  TX_sync_Exemples
Deux lignes, ou le temps réel ne marchera jamais et rien ne le dira à l'écran.
7
Exploitant Relancer le poste, puis écran de connexion. Sur une base vide, il se transforme en création du premier compte : identifiant, nom complet, mot de passe.
Attendu Le rôle de ce premier compte est Administrateur, forcé dans le code — aucun choix n'est proposé, volontairement. À la connexion : votre nom et « Administrateur » dans la barre latérale, et les trois entrées (Tableau de bord · Exemples · Rôles et permissions).

Et si ça ne démarre pas

SymptômeCause la plus sûreVérification
L'assistant se rouvre à chaque lancement Réglages non écrits, ou fichier cabossé (le socle repart alors à vide, sans [ERR]) Exploitant ouvrir %LocalAppData%\{NomApplication}\settings.json
« Server does not exist / connection refused » Hôte ou port erroné, service PostgreSQL arrêté, pare-feu Bouton Tester de l'assistant ; le message cite le SQLSTATE traduit
« password authentication failed » à la migration Le terminal ne relit pas les réglages enregistrés avant la commande Relancer l'assistant puis dotnet ef database update
Base absente et création refusée Nom de base hors whitelist (caractères non autorisés) Renommer en lettres/minuscules/tirets bas, réessayer
Compte gelé après trois échecs Anti-force-brute normal : 60 secondes, horloge du cadre Attendre, ou Exploitant en SQL : UPDATE "Comptes" SET "EchecsConsecutifs"=0, "GelJusqua"=NULL;
Le poste affiche « 0 ligne » alors qu'un autre voit des données Trigger de synchro absent, ou SyncChannel différent entre postes Étape 6 ci-dessus ; puis pièges mesurés
Journal du poste

Serilog écrit dans %AppData%\{NomApplication}\Logs\app-{date}.log — un fichier par jour, quinze conservés, niveau Debug. Une erreur technique ne s'affiche jamais brute à l'écran : la trame complète est dans le journal, la phrase française est sur le poste.
