Règle de dépendance

WPF → Common → Core et WPF → Data → Core. Data et Common ne se référencent jamais entre eux — la jonction se fait au composition root (App.xaml.cs). Un projet qui remonte vers l'UI est une faute d'architecture, pas une nuance.

Cycle d'une écriture, puis d'une notification

Décrire le trajet complet évite deux erreurs classiques : garder un contexte vivant dans un écran, et croire qu'un bouton grisé protège quelque chose.

1. Le poste écrit

1
Poste ExempleViewModel.EnregistrerAsync() valide les champs, puis _autorisation.Exiger(Droits.ExemplesModifier) — la vraie garde.
2
Poste _portes.CreateAsyncScope() : une portée DI par opération, libérée en finally. L'écran ne retient aucune connexion du pool.
3
Poste IUnitOfWork.Repository<T>() → SaveChangesAsync() : le contexte écrit l'audit (CreatedAt/UpdatedAt) et convertit un Remove en IsDeleted = true.
4
Base Le trigger TX_sync_{table} appelle framework_notify_sync() et émet pg_notify('framework_sync', …) avec la table, l'opération, l'horodatage et l'Application Name de l'émetteur.

2. Les autres postes se rechargent

1
Poste PostgresSyncListener (connexion dédiée, hors pool) reçoit la notification et la compare à son propre ClientSyncId : anti-écho.
2
Poste L'événement ISyncNotificationService est publié par App.xaml.cs dans le WeakReferenceMessenger sous forme de ExternalEntityChangedMessage.
3
Poste Chaque écran IRecipient<…> filtre sur sa table, ignore la notification s'il est en cours d'écriture, puis se recharge sur le Dispatcher.
4
Poste Le shell incrémente son compteur et affiche « Dernière notification : table (opération) ».
Le maillon que l'on oublie

Une nouvelle table métier n'est pas partagée tant que sa migration n'a pas ajouté migrationBuilder.Sql(SyncNotifySql.Script("framework_sync", new[] { "MaTable" }));. Sans cette ligne, rien ne se casse : les postes se croient simplement seuls pour toujours.
