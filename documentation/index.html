Convention de mise à jour — contractuelle

La documentation n'est pas une photo : elle est tenue au même titre que le code. La règle est simple et tient en trois lignes.

QuandQui agitQuoi
Chaque brique livrée (commit feat(...)) Agent Mettre à jour 01-structure/architecture.html (table des briques), 03-plan/feuille-de-route.html (statut), l'en-tête de index.html (commit, nombre de tests) et le Framework_Blueprint.md.
Chaque page jouée en manuel Exploitant Renseigner la fiche de recette : verdict, date, rôle testé. Une anomalie se signale par « numéro du parcours, écran, phrase exacte affichée ».
Avant une mise en production produit Agent Relire chaque page contre le code, corriger les écarts, puis dater l'en-tête de la version livrée.
Source de vérité

Framework_Blueprint.md, à la racine, reste le document de travail de l'agent : quand une page HTML et le blueprint divergent, le code a raison, puis le blueprint, puis la page. La page conventions et pièges en est la traduction lisible et doit être régénérée quand le blueprint change.

Comment lire ce dossier

  • Vous découvrez le socle → architecture, puis plan de qualification.
  • Vous démarrez un produit → nouveau produit en deux heures, puis cahier des charges pour décider ce qui est à votre charge.
  • Un poste se comporte mal → pièges mesurés (la faute y est presque toujours décrite), puis le parcours T correspondant.

Règle de lecture commune à toutes les pages

Chaque étape d'une recette porte un badge qui dit qui l'exécute. Un texte sans acteur est une ambiguïté, pas une indication.

BadgeSignification
Exploitant Vous, au clavier, dans l'interface ou dans un terminal.
Agent Moi, dans le dépôt : code, tests, build, commit, et documentation.
Poste Le programme lui-même, sans intervention (démarrage automatique, écoute LISTEN/NOTIFY).
Outil Une ligne de commande externe : dotnet, dotnet ef, psql.
